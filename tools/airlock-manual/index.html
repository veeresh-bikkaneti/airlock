01

What Airlock actually is

Never touched a tool like this before? Good — start exactly here. Everything after this section assumes you already know what's below.

An AI coding assistant (like Claude Code) normally works by sending your questions to a company's servers over the internet, and a powerful model there sends back an answer. That's simple, but it means two things: your code and questions travel over the internet, and you're paying for (or limited by) however much that company lets you use.

Airlock lets you run a similar AI model directly on your own computer instead — using a free, open-source program called Ollama that downloads and runs AI models locally. Nothing has to leave your machine. Airlock is the layer of commands wrapped around Ollama that makes this comfortable to use day-to-day: starting it up safely, checking it's healthy, letting other tools (like Claude Code) talk to it, and shutting it down cleanly.

🚪
Why it's called Airlock

A real airlock is a small chamber with two doors that are never both open at once — you're either sealed inside, or sealed outside, never halfway between. This tool works the same way: by default, everything stays local and sealed in. If you ever want to reach out to the cloud — a fallback provider, a subscription service — that's a deliberate, separate switch you flip on purpose, not something that happens by accident.

Everything in Airlock is typed into a terminal (see the glossary below if that word's new to you) as short commands that all start with ai-, like ai-start or ai-doctor. You don't need to know PowerShell, Python, or any programming language to use them — you just type the command name and press Enter.

02

Words you'll see on this page

Every jargon word on this page has a card here. Click or tap to flip it — plain English on the back, no dictionary required.

CLIflip →

Short for "command-line interface" — a way of controlling a program by typing words instead of clicking buttons. Every Airlock command is a CLI command.

Terminal / Shellflip →

The window where you type commands (PowerShell, in Airlock's case). Closing it ends anything that was only set up "for this session."

Environment variableflip →

A small labeled note your terminal session carries around, like ANTHROPIC_BASE_URL. Other programs read these to know where to send requests.

Portflip →

A numbered "door" a program listens on for connections. Ollama listens on one, so other tools know exactly where to knock.

Firewall ruleflip →

A guard that decides what's allowed through a port. Airlock adds one that blocks anyone outside your machine from reaching your local model.

Backendflip →

The program actually doing the AI work — Ollama or vLLM. Everything else in Airlock is a layer that starts, checks, and talks to it.

Modelflip →

The AI itself — e.g. qwen2.5-coder:7b. A file of learned patterns that turns your prompt into a reply. Bigger isn't always better; it has to fit your hardware.

APIflip →

A fixed way for programs to talk to each other — like a restaurant menu you order from. Your backend exposes one; Airlock's commands are the customer.

Sessionflip →

Everything between opening a terminal and closing it. Many Airlock settings are deliberately session-scoped so they can never outlive it.

Embeddingflip →

A list of numbers that represents the meaning of a piece of text, so a computer can measure how similar two pieces of text are.

Vector databaseflip →

A filing cabinet built specifically to store embeddings and quickly find the closest matches to a new one. Airlock uses one called Chroma.

RAGflip →

"Retrieval-Augmented Generation" — looking something up before answering, instead of answering from memory alone. The vector database is the "looking up" part.

03

How the pieces fit together

Five layers, stacked like the airlock it's named for — each one only ever talks to its neighbor. Hover the diagram to pause the drift and read at your own pace.

layer 1
You, in a terminal
Type an ai-* command and press Enter.
layer 2
Airlock CLI (profile-helpers.ps1)
Turns that command into the right action — start, stop, check, redirect.
layer 3
Your local backend (Ollama or vLLM)
Runs the actual model, on one fixed port, behind a firewall rule.
layer 4 · optional
memory-service
Turned on with ai-memory-on. Sits between your chat client and the backend, adding recall of things said earlier.
layer 5 · gated
Cloud providers
Only reached if you explicitly set up a fallback key — never by default, never silently.

Each layer only knows about the one next to it: your terminal talks to the CLI, the CLI talks to the backend, and the backend never knows or cares whether the cloud layer exists at all. That separation is what makes "local by default, cloud only on purpose" an actual guarantee instead of a promise.

💡
When this picture matters

You're deciding whether it's safe to turn on a cloud fallback provider, or explaining to a teammate why your code never leaves your machine by default. This diagram is the answer: there's a real, gated layer 5 the cloud has to pass through, not a background connection you have to take on trust.

04

Scaling beyond local: cloud provider keys

Layer 5 from the diagram above, in practice. Local is the default because it's free and private, but sometimes you want a stronger model for one hard problem, or your own hardware just isn't enough. Here's exactly how to add a key, and — just as important — exactly what currently happens with it once you do.

Adding a key

powershell 
PS> ai-auth-set openrouter sk-or-v1-xxxxxxxxxxxx
# supported names: openrouter, openai, anthropic, google, nvidia
PS> ai-policy   # see which providers are configured

ai-auth-set writes to ~/.ai-platform/config/auth.json — a file kept outside the repo and outside git entirely (it's in .gitignore). That's the one supported way to add a key: never hand-edit an environment variable for this, and never put a key in any tracked file.

💡
When you'd want this

You're deep into a large, multi-file refactor your local model keeps stumbling on, or your machine simply can't fit a model big enough for the task at hand. A cloud key is the escape hatch for that specific moment — not a replacement for local by default.

📡
What "scales" actually means here

This isn't autoscaling infrastructure — there's no fleet of servers spinning up. "Scaling" for a single-machine tool like this means one thing: swapping which model answers a given request, from a small one that fits on your GPU to a much larger one that runs on someone else's. Storing a key is step one of that swap. Whether a swap actually happens depends on which command you're using — covered honestly below, not glossed over.

06

The commands

Every command starts with ai-. Type it, hit Enter — that's the whole learning curve. Below: what each one actually does, the exact snippet, and a real moment you'd reach for it.

ai-start

Starts your local model backend and gets it ready to use.

ai-stop

Shuts the backend down cleanly and clears session state.

ai-doctor

Diagnoses connection problems and tells you the exact fix.

ai-claude-on / -off

Points Claude Code at your local model, for this terminal only.

ai-memory-on / -off

Turns retrieval-augmented memory on or off for your chats.

ai-uninstall

Removes Airlock from your machine, with a safe preview first.

ai-start — get your local model running

Run this once at the start of a work session. It checks for any leftover Ollama processes and closes them, starts one clean instance on a fixed local port, and puts a firewall rule around that port so nothing outside your machine can reach it.

powershell 
PS> ai-start
# picks a model that fits your hardware and starts it — takes a few seconds
💡
When you'd use this

You've just opened your laptop and want to start coding with a local model. ai-start is the first thing you type — everything else in Airlock assumes the backend from this command is already running.

Want a specific model or backend? Add flags:

powershell 
PS> ai-start -Model qwen2.5-coder:7b
PS> ai-start -Backend vllm   # if you have an NVIDIA GPU + Docker Desktop

ai-doctor — find out why something won't connect

If Claude Code, or any other tool, seems to be talking to the wrong place — or won't connect at all — run this. It checks every place a "point this tool at localhost" setting can hide, and prints the exact fix in plain language, instead of you hunting through settings by hand.

powershell 
PS> ai-doctor
💡
When you'd use this

Claude Code shows a connection error, or a tool behaves like it's talking to nothing. Before checking anything by hand, run ai-doctor — it tells you what's set, where, whether it's actually broken or just stale, and exactly what to do next.

🔧
Two kinds of problem it tells apart

A setting can be broken in two different ways that look identical from the outside. A dead redirect is a light left on in a room you're not in — you can just walk over and switch it off yourself. An orphaned pointer is a light wired in by something else entirely, still fed by a circuit you can't reach from where you're standing — clearing it here does nothing; you have to close the whole session (sign out or reboot) to actually kill it. ai-doctor tells you which one you're looking at, so you don't waste time on the wrong fix.

ai-claude-on / ai-claude-off — use Claude Code with your local model

This points Claude Code at your local model instead of the cloud, for this terminal window only. It's checked as actually working before anything is switched, and it undoes itself automatically the moment you're done — no file on disk is ever edited.

powershell 
PS> ai-claude-on
PS> claude   # use Claude Code exactly like normal from here
PS> ai-claude-off   # or just close the terminal — same result
💡
When you'd use this

You want to code with Claude Code without spending your cloud subscription's usage, or you're working somewhere without a reliable connection. ai-claude-on switches this one terminal over; every other terminal, and Claude Code everywhere else on your machine, is unaffected.

ai-memory-start / ai-memory-on / ai-memory-off — give your chats memory

Turns on an optional add-on called memory-service: your model can recall relevant things you or it wrote down earlier in the same project, instead of starting fresh every message. Covered in full depth further down this page.

powershell 
PS> ai-memory-start   # turn the service on, once
PS> ai-memory-on       # route your chats through it
PS> ai-memory-off      # back to a direct connection, any time
💡
When you'd use this

You're working on the same project across several sessions and want the model to remember decisions or context you've already established, instead of re-explaining them every time.

ai-stop — shut everything down cleanly

Stops the backend, clears session state, and undoes any active ai-claude-on redirect in that shell — the tidy opposite of ai-start.

powershell 
PS> ai-stop
💡
When you'd use this

You're done for the day, or you want to free up the RAM/GPU your local model was using for something else.

ai-uninstall — remove Airlock from your machine

Removes what the installer put in place: the installed copy, the source clone it was built from, the line in your PowerShell profile that loads Airlock's commands, and any firewall rules it created. Your models and Ollama itself are left completely alone — those are yours, independent of Airlock.

powershell 
PS> ai-uninstall -WhatIf   # preview only — nothing is touched
PS> ai-uninstall          # do it for real, once you're sure
💡
When you'd use this

You're setting up a new machine and moving your workflow there, or you've decided Airlock isn't for you. Run it with -WhatIf first to see the exact list of what would be removed, with zero changes made — then run it again without the flag when you're ready.

The very first thing it does, before removing anything, is check this terminal for a leftover setting — the same check ai-doctor runs — so you get that information while everything is still in place to look at.

07

Launching the 3D system visualizer

A second standalone tool in this repo, separate from the ai-* commands above: a 3D scene at tools/3d-system-visualizer/index.html that draws a system — services, data stores, and the edges between them — as an explorable node graph, with animated workflow playback: a glowing packet travels the actual call path, step by step.

🧊
How it's different from the diagrams on this page

Everything animated earlier on this page is a fixed, hand-drawn picture of one specific flow in Airlock's own code. The 3D visualizer is a general-purpose tool — point it at a {nodes, edges, flows} JSON file describing any system, including your own projects, and it draws and animates that instead. It ships with a demo scene, and a way to generate a scene from this platform's own real activity (below).

Starting it

One real requirement: it loads Three.js from a CDN via an import map, which needs an actual HTTP origin — opening index.html straight from disk (file://) will fail to load. Serve it over a local HTTP server instead, from the repo root:

powershell 
PS> python -m http.server 8347 --directory tools/3d-system-visualizer
# or, if you have Node:
PS> npx serve tools/3d-system-visualizer

Then open http://localhost:8347 and click a workflow button in the top-left panel to watch it animate through the graph. Click any box or connector for a metadata panel — nodes carry a healthy/degraded/down status that glows amber or red right in the scene, so a problem reads at a glance without clicking anything.

💡
When you'd use this

You want to explain your own system's architecture to someone — or to yourself, six months from now — as something explorable rather than a static diagram, including which call paths actually exist and which services depend on which.

Seeing Airlock's own real activity, not just the demo

Generate-LiveScene.ps1 reads this platform's own audit log (~/.ai-platform/logs/<date>.jsonl) and turns what actually happened — backend selections, model pulls, firewall guards, starts and stops — into a scene using the same schema, registered automatically so it shows up in the picker.

powershell 
PS> .\tools\3d-system-visualizer\scenes\Generate-LiveScene.ps1
# then pick "local-ai-platform (live)" from the Scene dropdown in the browser,
# or open http://localhost:8347/?scene=scenes/local-ai-platform-live.json directly

It's a snapshot, not a live stream — re-run it after a session to refresh with whatever happened since.

08

The memory service, in depth: RAG, the vector database, LangChain, and LangGraph

Airlock ships an optional component called memory-service — a small program that sits between your chat client and your local model. This is the one place in Airlock that does retrieval-augmented generation, using the pieces defined in the glossary above. Here's exactly how it works.

💡
When you'd want this on

You're going back and forth on the same project across several separate chat sessions this week, and you're tired of re-explaining decisions you already made yesterday. Turn it on with ai-memory-start and ai-memory-on (see the commands section above) — this is what those two commands actually turn on, underneath.

📋
RAG in one sentence

Before the model answers you, a librarian (memory-service) checks a card catalog (the vector database) for anything relevant that was written down earlier — and only whispers it to the model if it's a genuinely close match. If nothing in the catalog is close enough, the librarian says nothing at all rather than handing over a card that's probably wrong. That "say nothing rather than guess" rule is called failing closed, and it's the most important design decision in this service.

Precision check — what's actually LangChain here

"LangChain" often implies chains, retrievers, and agents. In this repo it doesn't. requirements.txt pulls in langchain-core only as a dependency of LangGraph — there is no LangChain chain, retriever, or agent anywhere in this codebase. Retrieval is a direct call to the vector database. The embedding step is hand-written, not LangChain's default:

  • Why hand-written embeddings. LangChain's default embedding backends reach for a cloud provider. That would send your conversation content off your machine, which goes against this platform's local-first design. So the embedding step talks only to the Ollama instance Airlock itself manages — never a cloud endpoint.
  • langsmith is installed and deliberately switched off. It's LangGraph's tracing/telemetry client, and it can transmit externally if enabled. It's turned off explicitly at startup, so tracing needs a deliberate decision to turn on, not just an unset variable somewhere else on the machine.
  • LangGraph is the actual orchestrator. It's a small two-step sequence (below) — not because the pipeline is simple, but because it doesn't need to be more than that yet.

The request path, step by step

Every chat message that comes in through memory-service takes one of two paths, decided by a single check: is the active backend Ollama? Ollama can produce embeddings; vLLM can't. So when vLLM is active, retrieval simply can't run — the service degrades to a plain passthrough rather than erroring, or worse, reaching for a cloud embedding service to keep going.

Two stores, two keys, no shared row

"Memory" sounds like one thing, but it's two separate stores here, each with its own key, and they are never joined in storage — only for a moment, at request time, by whatever you send in.
